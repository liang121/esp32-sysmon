# ESP32 HTTP 大包丢失修复设计

## 目标

让当前 ESP32 与 Mac 的局域网 HTTP 取数稳定，保留现有 Wi-Fi 配置、Mac 地址、Monitor UI 与 API 协议。

## 已确认的故障层级

设备已连 Wi-Fi、拿到 IP，目标 IP 与 Mac 当前接口相符；Mac 服务监听 `8787`，本机访问 `/api/now` 返回 200，macOS 防火墙未开启。Mac 到设备的小 ICMP 包能通。抓包显示 ESP 向 Mac 建立 TCP、Mac 回包，但 1440 字节数据段反复重传而没有得到 ESP 的确认。按 4 次一组测试，512～640 字节的 ICMP payload 全部收到，768 字节开始丢，1000 字节全部丢。因此故障位于设备接收大包的局域网路径，而非 Mac API 进程或互联网访问。

## 方案与取舍

ESP-IDF 当前 `CONFIG_LWIP_TCP_MSS=1440`。先降到 576，使对端按设备声明的 MSS 分段，避免 Mac 向 ESP 发送在当前链路上丢失的大数据包。这会增加包数、降低峰值吞吐，但设备每秒只取约 1.7 KB JSON，吞吐代价很小。先单独验证此改动；若仍有小包丢失导致连接超时，再根据抓包与串口日志评估 HTTP 超时、请求频率或网络/AP 故障，不把这些变量一次混改。

刷入后抓包确认 Mac 的 TCP 数据段最大为 576 字节，ESP 持续确认接收；首次 30 次设备状态采样有 29 次 `ok`，另一次串口输出无法解析，随后 60 次连续采样全部为 Wi-Fi 在线且 `last=ok`。此前丢失的 1000 字节 ping 在重连后也恢复，因此不能仅凭这组观察断言 AP 存在固定的 MTU 限制。仍需区分缩小 MSS 与刷机后重连各自的作用，并持续观察是否复发。若其它设备或协议也出现大包丢失，应继续检查 AP/漫游链路。
